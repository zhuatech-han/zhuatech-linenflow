# LinenFlow · 酒店布草洗涤与交接对账

**0.1.0 · 知华科技公开源码学习版／非商业源码版。未经书面授权不得商用。**

洗涤厂清点了多少件，酒店收回了多少件，返洗、报损和拒收各在哪里？LinenFlow 将酒店自有布草的送洗声明、工厂实收、独立质检、分批配送、酒店签收和月度对账连成一条可核对记录。适合工业洗涤运营、酒店后勤及企业软件实施团队在隔离环境学习评估。中文 / English，电脑与手机使用同一套真实后端。

## 一批布草，从送出到对账

```text
酒店送洗草稿 → 提交冻结约定价 → 工厂实物清点 → 酒店确认差异
                                                ↓
                                             洗涤执行
                                                ↓
                                    独立质检 → 返洗 → 再质检
                                                ↓
                                      合格布草分批配送
                                                ↓
酒店核对签收 → 拒收实物由工厂独立核验退回 → 可再次配送
      ↓
全部合格件签收＋报损结果核对 → 酒店确认整批完成
      ↓
按完成月份汇集未计费批次 → 出账 → 酒店确认／异议
      ↓
已发生线下收款分笔登记 → 结清；录错款项独立冲正，保留原记录
```

送洗声明不等于工厂实收。即使数量一致，也由绑定酒店的账号确认清点后才开洗。管理员不能代酒店签收或确认账单。

每次质检的 **合格＋待返洗＋报损＝工厂实收**。已经合格和已报损数量不可在下一轮质检减少；质检人与当前洗涤执行人不同。返洗不增加实收量，不额外重复计费。

酒店部分拒收时，未签收部分继续占用配送预留，工厂核实全部拒收实物退回后才释放。退回核验人与原发货人不同。交接记录和清点说明保存人工提交的事实，系统不替代实物核验，也不构成电子签名。

**计费＝已确认完成批次的签收合格件数 × 提交时冻结单价。** 本版固定人民币、按件计价；返洗和报损不计洗涤费。账单按上海时区的批次完成月份归集，每批次最多关联一张有效账单。异议账单可以取消后重新归集；原账单及关联历史仍保留。

## 岗位与操作

| 岗位       | 已实现的操作                                                                                                           |
| ---------- | ---------------------------------------------------------------------------------------------------------------------- |
| 酒店客户   | 本酒店送洗草稿增删改查、送出与取消、实收确认／退回重数、分批实际签收、整批完成确认、账单确认／异议、本人酒店统计与导出 |
| 收货与生产 | 本部门送洗编制、工厂清点、开洗与返洗、独立实物退回核验                                                                 |
| 质检       | 本部门逐品类合格、返洗、报损登记；数量守恒及岗位分离                                                                   |
| 配送       | 本部门分批发出；扣除已签收与未解决交接的预留，阻止超发                                                                 |
| 财务       | 酒店与约定价、完成批次月度归集、出账、取消、分次已收款登记、独立全额冲正、余额统计                                     |
| 管理员     | 部门、账号与酒店绑定、角色与接口权限、菜单、权限目录、品类字典、系统参数、主数据、操作审计；最后管理员及历史引用保护   |

业务目录有搜索、状态筛选、分页和有限排序。详情显示数量、单价凭据、清点与质检说明、配送单、款项和业务事件；可导出当前有权读取的 JSON 快照。管理员可修改注册权限的说明及菜单名称、顺序和所需权限；新增角色只能选择服务端注册的真实权限。

默认工厂岗位按部门隔离，酒店账号必须绑定客户，绑定优先于 ALL／DEPARTMENT／SELF 角色范围。工厂自定义 SELF 仅查看本人编制或执行的批次、本人编制的账单；不能以隐藏菜单代替接口鉴权。绑定酒店的账号即使被分配管理权限，也不能读取工厂管理目录或全部门审计。

### 全新数据库启动

```bash
python3 scripts/init-env.py
docker compose config --quiet
docker compose up -d --build --wait
```

打开 **http://127.0.0.1:8124/**，健康检查 **http://127.0.0.1:8124/actuator/health**。初始账号 `admin`，独立随机密码读取本机被 Git 忽略的 `.env` 中 `ADMIN_PASSWORD`。生成器以 0600 权限创建配置，不显示密码，也不覆盖已有文件。空库仅初始化总部、岗位、权限、菜单、三类布草字典及参数；不虚构客户或洗涤事实。已有数据库重启不重置账号或业务。

先建立部门、酒店、布草品类与客户约定价，再建立工厂岗位和绑定酒店账号。角色、菜单和部门直接通过后台页面维护。步骤见 [操作手册](docs/操作手册.md)。

| 配置名称                                              | 含义                                                                  |
| ----------------------------------------------------- | --------------------------------------------------------------------- |
| `DATABASE_PASSWORD` / `MYSQL_ROOT_PASSWORD`           | 应用数据库／MySQL 初始化密码，必须配置，不能使用共享生产口令          |
| `ADMIN_PASSWORD`                                      | 仅空库管理员初始化使用；至少12位含大小写与数字，BCrypt 输入最多72字节 |
| `WEB_PORT` / `BIND_ADDRESS`                           | 默认8124／127.0.0.1；端口冲突时改为可用端口再启动                     |
| `COOKIE_SECURE`                                       | 本机 HTTP 为 false；正式 HTTPS 入口设为 true                          |
| `DATABASE_URL` / `DATABASE_USER` / `DATABASE_CATALOG` | 单独运行后端时覆盖连接地址、用户及实际数据库名                        |

MySQL 不向主机发布端口，容器按健康顺序启动；前端代理使用后端服务名。生产入口需由部署方配置 HTTPS、访问控制和备份。核心业务无需第三方密钥。

不用容器开发：准备独立 MySQL 8.4 数据库 `zhuatech_linenflow` 和用户，设置上表数据库及管理员环境变量后在 `backend` 执行 `mvn spring-boot:run`；另在 `frontend` 执行 `npm ci` 和 `npm run dev`，访问 http://127.0.0.1:5173/，Vite 同源代理后端8080。

### 数据库与升级

完整 SQL：[V1 身份目录](backend/src/main/resources/db/migration/V1__identity.sql)、[V2 洗涤业务](backend/src/main/resources/db/migration/V2__laundry.sql)。客户、品类、单价、批次行、配送行、账单关联、款项、事件和幂等凭据均持久化，外键保护历史，编号与收款凭据有唯一约束。JPA 仅验证结构，不自动改表。

所有业务写入和管理变更共享总部行锁，锁后重新读取当前身份及权限，再核对单据版本和 UUID。适合小型单实例团队；不承诺高吞吐或多租户 SaaS。默认最多1000批次，可在后台设置100–1000；最多1000账单，每批次50品类／200配送，每账单200款项，每业务对象1000事件。管理目录最多10000行，审计页面最多展示最近500条；超限明确拒绝，不静默截断统计。

升级前备份数据库与 `.env`，先在备份副本中验迁移、业务和健康；已有迁移不可改正文，后续增加更高版本。`docker compose down` 保留数据库，`down -v` 会删除数据，不得对正式数据直接执行。[部署与恢复](docs/部署手册.md) 提供具体步骤。

前端测试验证会话请求、数量输入、质检守恒及配送行。六类以上真实页面截图、完整镜像启动、实际业务和数据库验证仍是发布门槛；不能以构建成功代替业务验收。具体交付检查结果另附交付记录。

## 故障与安全边界

- 启动失败：查看 `docker compose logs --tail=100 backend mysql`，核对密码、端口、迁移和健康；不要跳过测试或删除正式卷。
- 无法登录：新库口令来自 `.env`，已有库使用最后设置的密码；连续8次失败限制5分钟。管理员重设密码会使原会话失效。
- 无法创建／提交：核对客户和品类启用状态、约定价、送洗日期及重复品类。提交后不能改写声明或价格。
- 清点／质检／配送失败：核对行号、整数件数、数量守恒、独立岗位、未解决配送预留和最新单据版本。
- 对账没有候选：只有酒店已确认完成、属于所选上海月份且未被有效账单占用的批次会归集。
- 账号与接口权限实时核对；会话采用 HttpOnly、SameSite=Strict、CSRF 和 BCrypt 12。不要把本机 HTTP 配置直接暴露到公网。导出和截图不得包含真实客户资料或凭证。[安全说明](docs/安全说明.md)

**本版未实现：** 布草资产租赁、押金、RFID／条码设备接入、逐件寿命、智能洗涤设备控制、称重计费、路线优化、真实银行支付、税务开票、电子签名、损失赔偿计算、附件上传、短信微信通知、离线同步、跨公司多租户。配送与收款均为人工登记外部已发生事实；系统不发起实际转账，也不自动核验到账。
